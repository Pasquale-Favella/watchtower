# Agent-started Delegated Tasks as linked Tasks

Status: accepted
Related: ADR 0039 (Task, Conversation and Run identity), ADR 0041 (per-dispatch loopback credentials), ADR 0042 (native delegated agents and side chats).

## Context

An Agent Run needs to hand work to another agent, possibly on a different Harness Connection, and to receive the result without the user relaying it. Harness-native subagents cannot cross harnesses, and side chats are user-initiated and return nothing to the parent.

## Decision

1. An Agent Run starts a child by calling an orchestration tool. The child is a new Task in the parent's Project with its own Conversation, Agent Sessions and Runs. A Delegation row links it to the parent Run. The parent Task's status is unaffected.
2. Any Harness Connection may be a target, including ACP connections. The orchestrator endpoint is attached over HTTP MCP when the agent advertises it, and otherwise through a stdio bridge that forwards to the same loopback endpoint. A connection that can neither attach it reports `delegation` as unsupported with a restriction.
3. The orchestrator endpoint is per dispatch, as ADR 0041 specifies: a random bearer token on 127.0.0.1, acquired in the Driver Connection scope. Its caller identity (Project, Task, Conversation, Run and access mode) is fixed when the endpoint is created. Tool arguments cannot change identity.
4. A child's access mode is at most its parent Run's access mode. An omitted request inherits and steps down when the target lacks the mode. An explicit unsupported request is refused, and an explicit escalation is refused.
5. Delegation depth is limited to 1. A Delegated Task receives no orchestration tools. An eligible parent Run can start any number of delegates. Each delegate starts immediately in its own Conversation. Each Conversation runs one Run at a time and queues follow-ups while busy.
6. A Delegation wake is a message queued into the parent Conversation with origin `delegation` on the existing follow-up queue. The existing hold rule applies: when the parent's last Run did not complete, the wake waits for the user. When the parent is idle and its last Run completed, the wake starts the parent Run.
7. `delegation_start` with `mode: wait` blocks up to `timeoutMs` (maximum 45 seconds). The waiter is registered before the child launches, so a child that settles during launch is still handed to the caller. A wait that times out keeps the result on its way to the parent through the wake.
8. A child's approvals stay in the child Task: the parent Agent cannot approve them. The parent may answer a child's question through `delegation_send`, and may read the child's latest messages and open question through `delegation_read`. The store updates live Delegation status and pending requests in the same transaction as the child Run change. A claimed or running child reads as `running`. A child awaiting input or holding a pending request reads as `waiting`. The coordinator records the final outcome when the child settles. `delegation_send` steers a running child, answers its open question, or resumes a settled child with a follow-up Run in the child's own Conversation. A resume re-opens the Delegation under the calling Run, inside the same transaction that checks the parent is live; its access mode is at most both the caller's and the child's previous mode, and its settlement queues a new wake. A send with a client request id repeats the action of its first call.
9. `delegation_cancel` is available to the direct parent. It requests cancellation, interrupts the child Run, drops its queued follow-ups, and disposes its wake. A cancelled Delegation settles as `cancelled`. A child whose Run was never claimed has no worker to report back, so its cancel settles the Delegation at once. Stopping a parent Run interrupts its running Delegations.
10. Delegation records and wake state live in the workspace SQLite store (migration 16). Recovery after a restart settles children whose Runs ended, re-queues wakes that are still pending, and settles a child whose Run was queued but never claimed as failed (`launch-failed`) with a wake for the parent. Recovery runs before the workspace opens when any Delegation is unsettled or any wake is pending, so no caller reads a child that is still queued after its Run ended. A wake's notice comes from the parent Run it queues, so it reaches the timeline whether or not that Run can start: promoting or claiming a Run and failing its launch advance the event watermark that bounds the timeline, since no driver event publishes those. A wake that was promoted into a parent Run which owner recovery then failed as never claimed stays `pending` and is owed again: recovery counts the lost delivery on the Delegation (`wakeAttempts`), so the re-enqueue uses its own command id instead of replaying the first receipt. A never-claimed child is not re-dispatched: the parent Run that asked for it has ended, so launching it after a restart would act with no caller. A child's launch and a cancel of it take the Delegation lock together, so a cancel that lands first prevents the launch.
11. The orchestration tools are `delegation_capabilities`, `delegation_start`, `delegation_status` (one Delegation, or a listing without an id), `delegation_read`, `delegation_send` and `delegation_cancel`. They run without a prompt in every access mode except approval-required, where only the reading tools do: delegation never widens a child past its parent, and Codex under its `never` policy would otherwise refuse each call. Claude allows the server through `allowedTools`, Codex through the server's `default_tools_approval_mode`, and ACP through the driver's permission answer. Where a prompt is due, Codex asks with an MCP elicitation, a field-less form; the Codex and ACP drivers show it as an approval and answer it, rather than refusing it as an unknown request. When the endpoint is attached, the Run also receives a short guidance block on when to delegate and how to reach the tools, which Claude and Codex defer out of the tool list: the Claude system prompt append, Codex developer instructions, or the first ACP prompt of each session the connection opens, in the variant for the agent behind it. The two entry tools are marked to load up front where the harness honours it.
12. Isolation defaults to `shared`, which reuses the parent checkout. `worktree` is opt-in and creates a worktree from the parent's branch.
13. Native harness children are unchanged (ADR 0042).

### Wake states

`pending` means the result is settled and the wake is queued or held but not yet in the parent Conversation. `delivered` means the parent's next turn carries the wake message. `disposed` means no wake is owed: a `wait` caller received the result directly, or the Delegation was cancelled. A `wait` that times out upgrades the record's wake from `settledOnly` to `always`, so the record shows the wake that settlement will queue. The desktop UI treats a settled Delegation with `pending` wake state and no active parent Run as held.

## Consequences

- Cross-harness delegation works without changing how native subagents render.
- Child Tasks are real Tasks. The sidebar does not list them: their parent's row rolls up their pending approvals, questions and running work, and opening a child reveals its parent row. A child whose parent is archived or missing is listed on its own. `listTasks` applies the same rule unless `includeDelegated` is set.
- Tool results are compact: an id, status, bounded result and a `next` hint. `delegation_capabilities` reports `available: "unlimited"` for eligible Runs and lists at most 20 models per connection, with `moreModels` counting the rest; its `search` filters each connection's whole catalog, so a model past the cap can be found and named. Prompts and results never enter the operational log.
- Plan-mode narrowing is not applied: Watchtower has no interaction mode to narrow.

## Alternatives rejected

- Store delegations in the side-chat JSON store: no run-level link, no outbox, no recovery.
- Let the parent Agent answer child approvals: the parent could widen a child's authority past the user's decision. Questions carry no authority, so the parent may answer those.
- Use only native subagents: cannot cross harnesses.
